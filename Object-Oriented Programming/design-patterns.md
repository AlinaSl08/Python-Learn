# Паттерны проектирования 

✅ **Паттерны проектирования** — это проверенные временем решения типовых задач. Они **не являются** конкретным кодом на каком-либо языке программирования и **не описывают** алгоритм решения задачи. Паттерны предлагают общую концепцию решения той или иной проблемы, возникающей при написании программ.

✅ **В классическом понимании** выделяют 23 основных паттерна проектирования, которые делятся на три главные категории:

+ **порождающие** — описывают способы создания объектов
+ **структурные** — описывают способы организации классов и объектов в более сложные структуры
+ **поведенческие** — описывают способы взаимодействия объектов и распределения обязанностей между ними

# Синглтон

✅ **Синглтон** — это **порождающий** паттерн проектирования, который гарантирует, что объект некоторого класса существует в единственном экземпляре, и предоставляет глобальную точку доступа к нему.

✅ **Возможная реализация синглтона**:

``` python
class Singleton:
    _instances = {}

    def __new__(cls, *args, **kwargs):
        if cls not in cls._instances:
            cls._instances[cls] = object.__new__(cls)

        return cls._instances[cls]
```
                 
✅ **Объекты-синглтоны** Python:

+ константа `None`
+ константа `True`
+ константа `False`
+ константа `NotImplemented`
+ литерал `...`

✅ **Плюсы паттерна**:

+ **Контроль экземпляров**. Паттерн гарантирует, что существует строго один объект определенного класса.
+ **Глобальный доступ**. Предоставляет удобную точку доступа к объекту из любой части программы.
+ **Ленивая инициализация**. Объект создается только один раз в момент первого обращения, что позволяет экономить ресурсы.
+ **Совместное использование ресурсов**. Все части программы работают с одним и тем же состоянием. Это позволяет, например, использовать одни и те же настройки во всей программе.

✅ **Минусы паттерна**:

+ **Глобальное состояние**. Любая часть кода может изменить состояние объекта, что затрудняет отслеживание ошибок.
+ **Сложность тестирования**. Синглтоны затрудняют написание тестов, так как сохраняют свое состояние между ними.
+ **Скрытые зависимости и сильная связность кода**. Классы, использующие синглтон, неявно зависят от него, из-за чего становится сложно вносить в них изменения.
+ **Проблемы при многопоточности**. В многопоточной среде паттерн требует специальной реализации, чтобы предотвратить одновременное создание нескольких экземпляров.

# Фабричный метод

✅ **Фабричный метод** — это **порождающий паттерн** проектирования, который определяет общий интерфейс для создания экземпляров класса, позволяя дочерним классам изменять тип создаваемого объекта.

✅ **Паттерн фабричный метод** помогает решить проблему жесткой привязки к конкретным классам создаваемых объектов. Для этого он предлагает выделить две группы объектов:

+ создатели
+ продукты

Создатели, как правило, содержат логику для работы с продуктами и один фабричный метод, который используется для создания этих продуктов. Сами продукты — это объекты, создаваемые фабричными методами.

✅ **Паттерн фабричный метод** следует применять, когда заранее неизвестно, какие типы продуктов и в каком количестве будут использоваться. Если потребуется добавить новый продукт, достаточно будет определить для него соответствующего создателя, а не вносить изменения в существующий код, что могло бы повлечь за собой цепочку ошибок.

✅ Ярким примером реализации **паттерна фабричный метод** являются классы `Path` и `PurePath` встроенного модуля `pathlib`. Этот модуль предназначен для работы с путями операционной системы и содержит следующую иерархию классов:

![](https://ucarecdn.stepik.net/a4c0b2ae-65d7-490d-8ce5-15871567e57b/.jpg)

Здесь классы `Path` и `PurePath` являются создателями, а все остальные классы — продуктами. В качестве фабричного метода у них выступает метод `__new__()`, который сам определяет, экземпляр какого класса нужно создать. Тип экземпляра зависит от используемой операционной системы.

✅ **Плюсы паттерна**:

+ **Слабая связанность**. Детали зависят от абстракций, а не от конкретных реализаций, благодаря чему соблюдается принцип инверсии зависимостей.
+ **Инкапсуляция**. Логика создания объектов изолирована в одном месте, что упрощает поддержку и изменение кода.
+ **Упрощение тестирования**. Благодаря тому, что создание объекта вынесено в отдельный метод, можно легко подменить реальную фабрику на тестовую и провести тесты, не затрагивая реальный объект.
  
✅ **Минусы паттерна**:

+ **Усложнение архитектуры**. Паттерн может привести к созданию сложной иерархии классов, так как для каждого продукта нужен отдельный создатель.
+ **Излишняя сложность для простых задач**. Если создаваемые объекты имеют простую структуру или процесс их создания полностью совпадает, использование фабричного метода может быть избыточным.
