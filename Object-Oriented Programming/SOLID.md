# Принцип единственной ответственности

✅ **Принципы SOLID** — пять основных правил объектно-ориентированного программирования, целью которых является написание понятного, гибкого и легко поддерживаемого кода.

✅ **Принципы SOLID** были озвучены **Робертом Мартином** в начале 2000-х годов, а акроним SOLID был придуман и введен Майклом Фэзерсом в 2004 году.

✅ Каждая буква акронима **SOLID** — это первая буква названия одного из принципов:

+ **S** (Single Responsibility Principle, SRP) — принцип единственной ответственности
+ **O** (Open/Closed Principle, OCP) — принцип открытости/закрытости
+ **L** (Liskov Substitution Principle, LSP) — принцип подстановки Барбары Лисков
+ **I** (Interface Segregation Principle, ISP) — принцип разделения интерфейсов
+ **D** (Dependency Inversion Principle, DIP) — принцип инверсии зависимостей

✅ **Принцип единственной ответственности** — это принцип, согласно которому каждый модуль должен иметь только одну причину для изменения. Причиной для изменения обычно называют изменение требований к приложению, из-за которых приходится менять его код, а модулем — связанный набор функций и структур данных.

✅ Изменений могут желать несколько источников требований, поэтому, говоря о причине для изменения, обычно имеют в виду группу источников, которую называют **актором**. **Актор** — это роль, которую играет группа источников требований по отношению к приложению.

✅ Для соблюдения **принципа единственной ответственности** модули проектируются так, чтобы каждый из них отвечал только за одного актора, то есть имел только одну ответственность и причину для изменения.

✅ **Божественный объект** — это объект, который имеет слишком много ответственностей. Он считается антипаттерном, которого можно избежать благодаря соблюдению принципа единственной ответственности.

# Принцип открытости/закрытости

✅ **Принцип открытости/закрытости** — это принцип, согласно которому программные модули должны быть открыты для расширения, но закрыты для изменения. Это значит, что при добавлении в модули нового функционала не должны вноситься изменения в существующий.

✅ **Основная идея** принципа открытости/закрытости заключается в следующем:

+ **открыты для расширения** — функциональность существующих модулей должна расширяться за счет создания новых модулей
+ **закрыты для изменения** — расширение функциональности одного модуля не должно приводить к изменениям в других модулях, которые его используют

✅ **Принцип открытости/закрытости** имеет два значения:

+ принцип открытости/закрытости Мейера
+ полиморфный принцип открытости/закрытости

✅ **Принцип открытости/закрытости Мейера** был сформулирован **Бертраном Мейером** в 1988 году. Согласно определению Мейера, суть принципа заключается в том, что однажды реализованный функционал модуля не должен подвергаться модификации. Исключением является только исправление ошибок.

✅ **Полиморфный принцип открытости/закрытости** основывается на строгой реализации интерфейсов, на наследовании от абстрактных базовых классов и на полиморфизме. Первоначальный интерфейс должен оставаться неизменным, а новые версии должны полностью ему соответствовать, но могут предлагать и новые функции.

✅ **Принцип открытости/закрытости** нарушается, когда поведение системы зависит от проверки конкретных типов данных, а не от полиморфного взаимодействия с объектами через единый интерфейс.

# Принцип подстановки Барбары Лисков

✅ **Принцип подстановки Барбары Лисков** — это принцип, согласно которому объект дочернего класса должен без каких-либо изменений в работе программы использоваться везде, где ожидается объект его родительского класса.

✅ **Принцип подстановки Барбары Лисков** был сформулирован Барбарой Лисков в 1987 году. Она является американским ученым в области информатики и лауреатом премии Тьюринга 2008 года.

✅ **Принцип подстановки Лисков** имеет близкое отношение к методологии **контрактного программирования** и ведет к некоторым ограничениям на то, как контракты могут взаимодействовать с наследованием:

+ предусловия не могут быть усилены в подклассе
+ постусловия не могут быть ослаблены в подклассе

✅ Дочерние классы должны сохранять **инварианты** — свойства объекта, которые должны оставаться неизменными на протяжении всего времени его существования независимо от конкретной реализации.

# Принцип разделения интерфейсов

✅ **Принцип разделения интерфейсов** — это принцип, согласно которому программные модули не должны зависеть от интерфейсов, которые они не используют. Другими словами, модули должны зависеть только от тех интерфейсов, которые они могут полностью реализовать.

✅ **Принцип разделения интерфейсов** помогает создавать интерфейсы, изменения которых влияют только на связанные модули. Для этого обычно разрабатывают более мелкие интерфейсы.

✅ **Принцип разделения интерфейсов** можно сравнить с принципом единственной ответственности. Разделение интерфейсов распределяет ответственность между ними.

# Принцип инверсии зависимостей

✅ **Принцип инверсии зависимостей** — это принцип, согласно которому программные модули должны зависеть от абстракций, а не от конкретных деталей реализации.

✅ **Программные системы** нередко состоят из двух типов модулей:

+ модули нижнего уровня
+ модули верхнего уровня 

✅ **Низкоуровневые модули** содержат базовую функциональность, например, подключение к базе данных. При этом они определяют, **как именно** нужно подключиться к той или иной БД, то есть содержат **детали** реализации, которые меняются в зависимости от БД.

✅ **Высокоуровневые модули** содержат более абстрактную бизнес-логику, к которой относится авторизация пользователей, отправка уведомлений, валидация банковских операций и многое другое. При этом они определяют, **что именно** должна выполнять система, не вдаваясь в детали реализации.

✅ **Принцип инверсии зависимостей** определяет связь между модулями нижнего и верхнего уровней:

+ модули верхнего уровня не должны зависеть от модулей нижнего уровня, оба должны зависеть от абстракций
+ абстракции не должны зависеть от деталей, детали должны зависеть от абстракций

✅ **Принцип инверсии зависимостей** можно сравнить с **принципом открытости/закрытости**: они похожи между собой, но решают разные уровни одной и той же проблемы — устойчивости к изменениям.

✅ **Инъекция зависимостей (Dependency Injection, DI)** — это паттерн проектирования, при котором объект получает необходимые ему другие объекты (зависимости) извне, а не создает их самостоятельно. Именно этот паттерн позволяет соблюдать принцип инверсии зависимостей.

✅ В программировании существует множество других принципов помимо SOLID. Например:

+ **DRY (Don't Repeat Yourself)** — принцип, согласно которому необходимо избегать дублирования кода
+ **KISS (Keep It Simple, Stupid)** — принцип, согласно которому необходимо стремиться к максимальной простоте решений
+ **YAGNI (You Aren't Gonna Need It)** — принцип, согласно которому необходимо избегать добавления функциональности, которая не требуется на данный момент
+ **Бритва Оккама** — принцип, согласно которому не нужно создавать лишние сущности без необходимости
